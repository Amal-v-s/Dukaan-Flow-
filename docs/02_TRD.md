# DukaanFlow --- Technical Requirements Document (TRD)

## 1. Technical Overview

Recommended stack: - Frontend: React + TypeScript; Vite; React Router. -
UI: Tailwind CSS or an equivalent token-driven component system; Lucide
icons. - Backend: Python + FastAPI. - Data store: Google Cloud
Firestore. - Deployment: Google Cloud Run. - Optional Phase 3 AI: Gemini
through Vertex AI. - Optional object/file storage: Google Cloud Storage,
only if required.

## 2. System Boundaries

The browser must not access Firestore using privileged credentials. All
business data operations go through the FastAPI service. The API
validates input, authorizes merchant ownership, performs calculations,
and returns DTOs. Forecast calculations are deterministic Python code.

## 3. Frontend Requirements

-   Desktop-first responsive shell with 240px sidebar, 72px top header,
    and 28--32px content padding at desktop widths.
-   Mobile adaptation with compact header and bottom navigation.
-   Pages: Overview, Customers/Khata, Suppliers, Transactions, Cash
    Flow, What-If Simulator, and Settings/More.
-   Use reusable components for metric cards, data tables, forms, status
    pills, empty states, dialogs, and charts.
-   All monetary values use a shared INR formatter and tabular numerals.
-   All forms expose validation and server errors accessibly.
-   Avoid placing business rules only in the client.

## 4. Backend Requirements

-   FastAPI application with versioned `/api/v1` routes.
-   Pydantic request/response models.
-   Service layer for customer ledger, suppliers, expenses, forecasting,
    and scenarios.
-   Repository/data-access layer isolates Firestore operations.
-   Centralized exception mapping and structured logging.
-   Health endpoints for liveness/readiness.
-   OpenAPI schema generated by FastAPI.
-   Configuration through environment variables; no secrets committed to
    source control.

## 5. Data Requirements

Core entities: businesses, users/memberships, customers, customer ledger
entries, suppliers, supplier bills, supplier payments, expenses, cash
accounts/balance events, forecast snapshots (optional), scenarios,
scenario events, and audit events.

For a hackathon seed-data mode, seed one demo business and related data.
Demo data must be distinguishable from user-created data and resettable
in development.

## 6. Forecast Engine Contract

Input: - Opening available cash at the forecast start. - Dated expected
customer collections. - Dated supplier payments and expenses. - Other
explicit cash inflows/outflows. - Safety buffer. - Forecast horizon (14
days for MVP).

Output: - One daily projected closing balance per day. - Dated
inflow/outflow totals. - Breach flags for zero and safety buffer. -
Contributor references for each breach. - Assumption metadata (estimated
vs confirmed/scheduled).

Formula:
`closing_balance[d] = opening_balance[d] + cumulative_inflows_through_d - cumulative_outflows_through_d`

Do not double-count a paid bill as both a planned outflow and a recorded
cash movement. Forecast only future cash movements that are not already
reflected in the opening balance.

## 7. API and Performance

-   List endpoints support pagination and filtering where practical.
-   Use server-side totals for dashboard KPIs.
-   Use consistent error responses and request IDs.
-   Keep Phase 1 query patterns compatible with Firestore indexes.
-   Set request timeouts and avoid unbounded collection scans.
-   Use idempotency keys for retry-prone money-movement creation if
    feasible.

## 8. Deployment

-   Frontend can be hosted on a static hosting service or served
    separately.
-   Backend deployed to Cloud Run.
-   Firestore in a selected Google Cloud project and region.
-   Use separate development and production configuration.
-   Cloud Run service account follows least privilege.
-   CI should run lint, type checks, tests, and build before deployment.

## 9. Environment Variables (examples)

Backend: - `ENVIRONMENT` - `GOOGLE_CLOUD_PROJECT` -
`FIRESTORE_DATABASE_ID` (if using a non-default database) -
`CORS_ORIGINS` - `APP_LOG_LEVEL` - `AUTH_ISSUER` / identity-provider
configuration when auth is enabled - `GEMINI_MODEL` only in Phase 3

Frontend: - `VITE_API_BASE_URL` - Public identity-provider configuration
only if a supported browser auth flow is implemented.

Never put service-account JSON, private keys, or server secrets in
`VITE_*` variables.
